# 术语一致表

长文档里同一个概念出现三种译法,读者会以为有三个概念。所以**术语表要先于
翻译建立**,并且是**唯一事实源**。

## 表里放什么

| 类别 | 例 | 备注 |
|---|---|---|
| 核心概念 | workspace → 工作区 | 全文只能一种 |
| 专有名词 | 角色(role) | 首次出现给原文,之后只用译文 |
| 缩写 | IDE、API、CLI | 首次出现给全称,之后用缩写 |
| 界面元素 | `Export` 按钮 | 界面里的字样**不译**,或译但保持一致 |
| 代码标识 | `exportSkills()` | **永不译**,原样保留并用等宽标注 |
| 不译的词 | Git、Docker、JSON | 译了反而增加认知成本 |

## 建表的顺序

1. **先扫全文,收集候选**(人名、产品名、界面词、缩写)。
2. **逐个定译**,并记**理由**(为什么不用更常见的那个译法)。
3. **把表放��项目里**(`glossary.md`),让后续所有人/机器复用。
4. **翻译时**发现表里没有的新词 ⇒ **当场补进表**。

第 4 条是纪律核心:表必须**跟着文档长**,否则第二篇就开始漂。

## 界面与文档的咬合

界面元素要**双向对齐**:文档里写「点击 Export」,界面上就得是 `Export`;
界面改成「导出」时,文档要同步改,不然用户找不到按钮。

- 引用界面时给出**界面上的原文**,必要时给位置(哪个面板、哪一段)。
- 用截图或控件路径代替「点击相应的按钮」。

## 一词多义要拆

同一个英文词在不同上下文对应不同概念时(例如 `run` = 运行/执行一次/跑测试),
**分条列出并给判据**:在什么语境用哪个。

不判据的话,译者会在两个词之间随机挑,读者跟丢。

## 数字与格式

- 保留原文的单位与格式习惯,或明确换算并在表里记。
- 日期、时间、货币符号按目标语言习惯改,但**同一篇里保持一致**。

## 最小示例

术语表(节选):

| 原文 | 译法 | 理由 |
|---|---|---|
| workspace | 工作区 | 不译为「工作空间」(那是另一种概念) |
| role | 角色 | 与 UI 文案一致 |
| sandbox | 沙箱 | 已有约定 |
| `exportSkills()` | 不译 | 代码标识 |
| run | 运行 / 执行一次 / 跑测试 | 按语境三选,判据:指界面按钮用「运行」;指一次回合用「执行一次」;指测试用「跑测试」 |

新发现:文档里还有 `check-out`(Git 的 checkout)⇒ 补进表:**不译**,首次出现
写「Git 的 checkout(检出)」,之后写 checkout。

**校验**:全文搜「工作空间」应 0 命中;搜「Export」应 0 命中(界面已改成
「导出」,文档也改了)。
