# 清洗报告

清洗最危险的地方是**它悄无声息**:原始表还在,中间结果看起来正常,没人知道
有多少行被丢掉了。所以清洗的交付物**不只是干净的数据,还有一份能对账的
报告**。

## 先备份,再动手

原始数据**只读**。清洗产出写到新位置(新文件/新表),并在报告里写明两者关系。
就地改原始数据是不可逆的,而且会让「这个数是怎么来的」再也答不上来。

## 逐条规则记账

每条清洗规则记四样:

| 字段 | 含义 |
|---|---|
| 规则 | 人话描述,能一句话说清 |
| 影响行数 | 命中多少行(不是百分比 —— 百分比会让人忽略绝对量) |
| 处理 | 删除 / 修正 / 标记保留 |
| 依据 | 为什么这么处理 |

**没有记账的清洗不许上线**。事后没人能回答「为什么少了 3 万行」。

## 分清「脏」和「异常」

- **脏**:格式错、编码坏、同一实体多种写法、必填为空 ⇒ 可以按规则处理。
- **异常**:值合法但不合业务常理(金额为负、年龄 200) ⇒ **不要自动改**。
  标出来给人看,让业务方判断。自动修正异常值会把问题藏起来,而且几乎总是错的。

## 保留可追溯的映射

- 合并重复实体时,保存**旧 id → 新 id 的映射表**。后面任何对不上的数,靠它回溯。
- 修正值时,尽量**加列**保存原值(`name_raw`),不要覆盖。

## 抽样人工核对

规则跑完,随机抽 20~30 条**人工过一遍**,尤其看:

- 合并规则:真的能判定是同一个实体吗?同名不同人呢?
- 去重规则:真的完全重复,还是同一条业务的不同阶段?

抽样发现的问题要回到规则里改,不是只改这一条数据。

## 交付

- 清洗后的数据 + 报告(规则表/影响行数/映射表位置/抽样结论)
- 报告里明确写:**哪些问题没有处理,以及为什么**(例如「供应商编码缺失
  12% ��— 需要对方补,已发邮件」)

## 最小示例

清洗目标:用户表合并重复账号。

- 备份:`users_raw_20261002.csv`(只读)
- 规则 1:同一 `email` 视为同一人 → 命中 412 行,合并为 380 人(32 组多人共用邮箱,
  保留最早注册的一条,其余 id 存 `merged_ids`)
- 规则 2:手机号格式非法(非 11 位)→ 命中 61 行,**标记保留不删**(`phone_valid=false`)
- 规则 3:姓名为空 → 命中 8 行,标记保留(其中 6 行有订单,不能删)
- 映射表:`user_merge_map.csv`(old_id → new_id)

抽样 25 条:规则 1 误判 2 条(同邮箱的夫妻共用邮箱)⇒ **规则收窄**:只有当
两份记录的 `name` 首字相同或都为空时才合并,重跑后误判 0 条。

**未处理**:61 条手机号非法 —— 需业务方回补,已发邮件,预计 3 天。
