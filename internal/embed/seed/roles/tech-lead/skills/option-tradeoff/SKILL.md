# 方案对比与任务拆解

面对有多种做法的技术决策,不要直接选一个开始干。**先把选项摆齐,再拆任务。**

## 第一步:把问题定义清楚

动手前用一段话写清:要解决什么、成功判据是什么、约束有哪些。
**判据说不清就不要开工** —— 那意味着你可能在解一个假问题。

## 第二步:至少给两个方案

每个方案写四行:

| | 方案 A | 方案 B |
|---|---|---|
| **改动面** | 动哪几个模块 | |
| **代价** | 工时 / 新增依赖 / 新增概念 | |
| **失败模式** | 它最可能怎么坏(不是泛泛的"可能有风险",而是具体的失败场景) | |
| **回滚** | 出问题怎么退回去;退不回去的(数据已改)要点名 | |

明确写出**「不做」的那些选项**与放弃它的理由 —— 否则同一件事会来回讨论。

标注哪些是推断、哪些已验证。没验证过的别写成结论。

## 第三步:拆任务

拆到「一个任务一次提交能做完」的粒度:

- 给出**依赖顺序**:哪些能并行,哪些必须等前面
- 每个任务写**完成判据**(可验证的产物,不是"处理完了")
- **风险最高的任务排最前**或单独跑。别把它放最后 —— 方向错了才发现,前面全白做

## 边界

- 不可逆操作(数据迁移、接口破坏、权限变更、对外发布)单独标出,写清影响面与验证方式。
- 涉及安全的取舍**从严**:能用更严的档位就不放宽,放宽要配显式开关与二次确认。
- 别为了显得周全而列五个方案。**两个能决断的 + 一个明确排除的**,比五个"可以考虑"有用。

## 最小示例

**需求**:"会话文件太多,列表打开很慢。"

**两个方案**:

| | A. 分页 | B. 按时间归档 |
|---|---|---|
| 改动面 | 列表接口加 `before/limit`;前端上滚加载 | 新增归档任务 + 前端加"查看归档"入口 |
| 代价 | 约 1 天,不动文件系统 | 约 2 天,多一个后台任务与状态 |
| 失败模式 | 上滚时新增会话导致分页错位(需去重) | 归档任务把"今天还在改的会话"误归档 |
| 回滚 | 关掉分页参数即退回全量 | 归档文件保留,可回填 |

**不做**:换数据库(为一个列表问题引入迁移成本,不划算)。
**推荐 A** —— 慢是读的问题,先改读;归档是写的问题,等量真的上来了再说。

**拆任务**:
1. 后端加分页参数(判据:`?limit=20` 返回 20 条 + `has_more` 标志)
2. 前端上滚加载(判据:滚到底自动加载下一页,重复 seq 被去重)
3. 前端空态文案(判据:没有更多时不再显示"加载中")

风险最高的是 2(分页错位),先做它。
