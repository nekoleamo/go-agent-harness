# 代码评审

只报**会真出事**的问题。不报风格偏好,不报"建议加测试"这种空话。

## 只报有证据的

每条问题必须给出:

- **`文件:行号`** + 引用那一两行原文
- **触发路径**:什么输入/什么时序下会出问题
- 不确定的,标注「不确定」并说明**为什么不确定**

一条"感觉这里有点问题"不是评审结论,是猜测。

## 优先级:真出事的先

| 档 | 含义 |
|---|---|
| **P0** | 丢数据 / 越权 / 死锁 / 静默失败(失败了但看起来成功) |
| **P1** | 真出错、契约与调用方实际用法不一致 |
| **P2** | 边界情况下的错误行为、性能陷阱 |

**静默失败永远排最前**:吞错、返回空结果、"成功"但没生效 —— 这类比崩溃难查十倍。

## 不报什么

- 纯风格、命名偏好、格式问题
- 泛泛的"建议加测试" —— 要说清**测什么行为**
- 无关紧要的重构建议
- 你没被要求看的范围(除非改动会影响它)

## 输出

- 按严重度分组,组内按文件位置排序
- 给**修法**(具体到改哪、怎么改),不只说"这里有问题"
- 明确区分「必须改」与「可选」,让作者知道优先级

## 边界

- 不为了让改动通过而降低要求;也不因为风格偏好阻塞合并。
- 同一类问题在多处出现,列全(或说明"共 N 处,模式相同"),不要只报第一处。

## 最小示例

**差的报告**:
> 这个函数看起来有点问题,建议重构一下。另外变量命名可以更清晰,建议加个测试。

**好的报告**:

> **P0 · 静默失败** — `web/server.go:412`
> ```go
> if err := svc.Save(p); err != nil {
>     return nil   // ← 错误被丢掉,调用方收到 nil 以为成功
> }
> ```
> 触发:磁盘满 / 配置目录只读时,保存失败但接口返回 200 + 空体 ⇒ 前端提示"已保存",
> 重启后配置回退。用户在不知情的情况下丢配置。
> 修法:`return fmt.Errorf("保存偏好失败: %w", err)`(这一处有三处同样问题:`Save`/`Update`/`AddWebAllowHost`)

差别:给了行号、给了触发场景、说了后果、给了修法、还指出同类共三处。
