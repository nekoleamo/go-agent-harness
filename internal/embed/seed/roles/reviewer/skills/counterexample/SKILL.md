# 反例构造

一条评审意见要成立,必须能回答:**在什么输入 / 什么时序 / 什么平台上,它会
出错?** 答不上来的不是缺陷,是风格意见 —— 混进报告里会让真正的问题被淹没。

## 提之前先造

对每一条候选问题,先写出**具体触发条件**:

- 输入:哪个值、哪个长度、哪个顺序(空? nil? 超长? 负数?)
- 时序:并发? 重入? 初始化前? 关闭后? 取消时?
- 平台:路径分隔符、大小写折叠、时区、权限位、字符编码

三条都答不上来,这条意见就**不该出现在报告里**。

## 造得出来才算数

给每个问题配一句「怎么炸」:

> 输入 `[名称为空]` 时 `Save` 走到 `os.WriteFile("")` ⇒ 返回 `open : no such file or directory`,错误直接冒到用户。

这是**可复核的**。评审者可以照着跑一遍,不需要相信你。

## 危险等级按后果分

| 级 | 判据 | 例 |
|---|---|---|
| P1 | 丢数据 / 越权 / 静默失真(用户以为成功了) | 写盘失败却返回成功 |
| P2 | 功能不可用 / 明显错误结果 / 卡死 | 并发下双写同一条记录 |
| P3 | 边界情况出错,影响可控 | 空列表时多画一条分隔线 |

按**后果**分级,不按修复难度 —— 改起来容易的那条不能因此往上抬。

## 不提的东西

- 风格偏好:命名、缩进、注释位置。既有风格不统一不是你的议题。
- 「建议」性质的改进:想法可以放附注,但不进问题列表。
- 没有触发路径的假想:「如果有人以后改了这里就会坏」不是现在的问题。

## 最小示例

候选意见:「这个缓存没有失效机制,以后可能拿到脏数据。」

**反例构造**:
- 输入:两次相同查询,中间数据库里的值被外部改了
- 时序:都在同一进程内,没重启
- 平台:无

跑出来了吗?没有 —— 缓存 TTL 是 30s,值在 30s 后自然被重取。**这条不成立**,
不进报告。

改成真问题:「缓存 key 里少了租户 id,同一实例服务多租户时会串。」
- 输入:两个租户查同名表
- 时序:任意
- 复核:单测:`Get(ctx, "t1", k)` 后 `Get(ctx, "t2", k)`,第二次拿到了 t1 的值

P1(静默拿到别人的数据)。
