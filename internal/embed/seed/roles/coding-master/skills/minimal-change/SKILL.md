# 最小改动

只做**解决当前问题所必需**的改动。范围纪律比聪明更重要。

## 动手前

1. 先读现有实现与测试,确认调用方与不变量。**不确定就查,不要猜 API 与字段名** —— 猜错的编译能过、运行才炸。
2. 说清改动点与影响面:哪些文件、哪些行为会变、哪些不会。涉及数据/接口/权限的,先说风险。
3. 判断这是**修 bug** 还是**加功能**:修 bug 要先能复现(写一个会失败的用例),否则你不知道自己修没修好。

## 改动时

- **不顺手重构**。看到旁边代码丑,记下来,不在这一轮动它 —— 重构会淹没 diff、引入无关回归,评审的人也看不出真正的改动。
- 与既有风格一致:命名、分层、错误处理方式照抄邻近代码,不要引入"我习惯的"新写法。
- 依赖能不引入就不引入。新依赖要回答:标准库能不能写?写出来多少行?维护成本谁担?
- **错误显式**。不静默吞错、不假装成功、不返回"看起来成功"的值。

## 什么时候可以超出范围

只有三种情况,并且要在交付里明说:

1. 改动**不完整就跑不起来**(比如新接口的调用点必须一起改)
2. 不改就**必然引入安全问题**(例如新的路径逃逸)
3. 现有测试**因为这次改动必然失败**,且失败原因是行为真的变了(不是测试过时)

## 交付前

- 跑测试。没跑就明说"没跑",不要用"应该没问题"代替。
- 看一眼自己的 diff:`git diff` 里有没有与本次问题无关的行。有就删掉。
- 说清**没做什么**:顺手能加但这次没加的东西,列出来让人决定要不要下一轮做。

## 最小示例

需求:"导出按钮点了没反应。"

**范围外的改动**(不该在这一轮做):顺手把 `exportAll()` 重命名成 `exportAllAsync()`、把相邻的 200 行老代码格式化、升级一个第三方依赖。

**该做的**:
1. 先写一个复现用例(点导出 → 期望落文件 → 现在失败)
2. 定位:读按钮的点击处理 → 找到它调用了一个已删除的旧函数
3. 改:接上新函数,保持原函数名不动(它有 6 个调用方)
4. 跑:新用例绿 + 该模块既有用例全绿
5. 交付时说:「顺手发现的两个可以一起清(见下),留给你决定要不要单独一轮」
