# 交付前自查

按清单过一遍。**每一条都要有答案**,答不上来的项要么去查,要么在交付里明说没做。

## 清单

| # | 项 | 怎么算过 |
|---|---|---|
| 1 | **编译过** | `go build ./...`(或项目对应的构建命令)。不是"我改的文件过了" |
| 2 | **测试过** | 跑了,且说清跑了哪些。**没跑测试要明说**,不能用"应该没问题"代替 |
| 3 | **新行为有用例** | 这次加的行为有对应用例;修的 bug 有**先失败后通过**的复现用例 |
| 4 | **错误路径想过了** | 输入为空/超长/类型错/文件不存在/权限不足,会怎样?报错对吗? |
| 5 | **没有静默失败** | 失败路径不会:吞掉错误、返回空结果、"成功"但没生效 |
| 6 | **并发安全** | 共享状态有锁?新加的 map/slice 有竞态?(`go test -race` 过一遍最省事) |
| 7 | **没留下调试痕迹** | `fmt.Println`、注释掉的代码块、`TODO(临时)`、改了没用的变量 |
| 8 | **文档同步** | 改了行为/命令/配置 → 对应文档改了(命令表、README、注册面) |
| 9 | **兼容既有口径** | 既有调用方还在用吗?接口变了吗?行为变了吗?变了要不要迁移? |

## 边界

- 清单不是形式:第 2 条说"跑了测试但没跑 `-race`"要写出来,不要含糊成"测试已通过"。
- 清单里某项**不适用**(比如纯文档改动没有第 6 条),直接跳过,不用假装做了。
- 有一项过不了又必须交付:明写哪一项、为什么、风险是什么。**别默默跳过**。

## 最小示例

交付时这样说(而不是"搞定了"):

> 改了 `parse()` 的空串处理。
> 1. 编译过(`go build ./...`)
> 2. `go test ./... -race` 全过,新增 3 条用例覆盖空串/纯空白/超长
> 3. 没跑 `test-windows`(本机没有 Windows 环境)—— 这条路径涉及路径分隔符,你在 Windows 上跑一下更稳妥
> 4. 发现 `parse()` 的调用方有一处仍在传 nil,会 panic;顺手改成传空串(属于"不完整就跑不起来"的情况)
